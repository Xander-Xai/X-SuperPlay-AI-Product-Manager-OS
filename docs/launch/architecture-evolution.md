# AI Web / SaaS 架构演进：不把快速上线变成未来技术债

## 目标

不是“所有 MVP 都用 Next.js”也不是“一开始就 Java 微服务”，而是明确**业务复杂度、团队规模、数据边界、故障隔离与真实成本**来选型。架构可以演进，但要为不可逆的数据和权限边界提前设计。

| 阶段 | 可选形态 | 优势/风险 | 保留的迁移接口 |
|---|---|---|---|
| 验证用户价值 | 静态站/Next.js 全栈或 FastAPI + 轻前端 | 开发快，复杂业务不宜提前微服务 | 独立的领域数据模型、API 契约、授权 |
| 首批真实用户 | 模块化单体：前后端、SQL 迁移、任务 Worker、AI adapter | 组织清晰、调试方便；避免把模型/数据库耦在页面里 | 版本化 API、数据库迁移、队列/事件契约 |
| 性能/安全确实瓶颈 | 拆推理、异步处理或高负载模块为服务 | 隔离负载但引入分布式故障和运维 | 幂等、Outbox/事件、Trace、灰度与回退 |
| 有证据的跨团队规模 | 在合适边界引入专门服务/栈（FastAPI/Java/Go 等） | 技术选择取决于生态和团队而非“高级感” | 兼容层、双写/回填风险/数据所有权 |

## 迁移成本的根本来源

- SQL 数据所有权/模式与迁移/回滚成本，而非“前端用哪种语言”本身；
- 业务规则掺杂在 UI/模型 Prompt 里，缺领域边界、契约和自动测试；
- 认证和授权没有统一执行位置，不能安全地拆服务；
- 异步任务缺幂等、状态恢复、可观测与降级；
- 依赖单供应商特殊接口未封装 adapter，无法替换模型/存储。

## 两个反例实战

**Case A：先 Next.js 后 FastAPI**：在模块化单体中定义 UI→API 的明确 DTO、数据迁移和权限策略，模拟将 AI 调用从 Next server 移到 FastAPI。旧客户端测试必须过，数据库留在原 owner，完成网关转发/回滚演练。无真实性能/团队理由则不迁移。

**Case B：从一开始 Java + 微服务**：如果业务只有几十个验证样本、团队一人、无高并发与组织约束，部署/监控/事务复杂度可能反而更高。先量化需要 Java 服务的具体业务前提：既有团队、系统接口、治理/运行环境或维护契约。满足后写 ADR 而非只凭偏好切换。

选型相关节点：ENG03 ENG04 ENG06 ENG09 ENG11 ENG12 OPS01 OPS02。参考 [Next.js 部署](https://nextjs.org/docs/app/getting-started/deploying) 与 [FastAPI](https://fastapi.tiangolo.com/deployment/concepts/)、[PostgreSQL](https://www.postgresql.org/docs/current/tutorial.html)。
