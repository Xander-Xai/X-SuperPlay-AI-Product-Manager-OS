# 产品经理全景：专业定义 × 大白话 × 产品使用场景

> 阅读目的：**建立脑中清晰模型，不要求读完再动手**。每个比喻只是帮助入门；正式做决策应回到定义、来源、真实约束和试验。以下比喻统一使用“经营一家餐馆”，便于对照。

## 先回答：产品经理到底干什么？

专业表达：产品管理围绕**特定用户需要与商业目标**，通过研究、取舍、跨职能协作和结果度量，持续判断应解决何种问题、采用何种方案、如何交付以及何时调整。Product Discovery 与 Delivery 不是一次性顺序交棒，而是一个持续循环。[SVPG](https://www.svpg.com/product-management-an-introduction/) / [Product Talk](https://www.producttalk.org/glossary-discovery-product-discovery/)。

大白话：产品经理**不是只画原型、写 PRD、追程序员进度**。你更像餐馆的经营负责人：知道顾客为什么来、菜单卖什么、不卖什么、厨房能否交付、顾客是否回来和店是否赚钱。AI 产品经理还要懂自动化的能力上限、成本和安全。

## 26 个核心概念，对照学习

| 专业术语 | 原理与正式定义（摘要） | 大白话 / 餐馆类比 | 关联知识节点与学习资料 |
|---|---|---|---|
| **Product Discovery 产品发现** | 发现用户需求、验证假设并决定值得开发的问题与方案 | 顾客进店前先研究他真正饿不饿、想吃什么 | `PM02`、`PM03`、`PM13` / [S27](https://www.producttalk.org/glossary-discovery-product-discovery/)、[S28](https://www.producttalk.org/getting-started-with-discovery/) |
| **Product Delivery 产品交付** | 将已验证方向转化为可发布、可靠、可维护的产品增量 | 把菜真正做出来、端上桌，还要保证食安和准时 | `PM17`、`OPS06` / [S26](https://www.svpg.com/the-product-operating-model-an-introduction/)、[S34](https://www.atlassian.com/agile/product-management/new-product-development-process) |
| **PM vs PO vs 项目经理** | PM 对价值与商业有效性负责；Scrum PO 对产品目标及 Backlog 的有效管理负责；项目经理重范围进度风险，真实组织可兼任 | 定菜品方向的是产品、决定下轮先做什么的是 PO、确保按时上菜的是项目经理 | `PM01`、`PM16`、`MGT02` / [S32](https://scrumguides.org/scrum-guide.html?lang=en)、[S25](https://www.svpg.com/product-management-an-introduction/) |
| **Outcome/Output** | Outcome 是用户行为或业务结果；Output 是产出的功能/活动 | 做了 10 个菜单是产出，顾客能快速点到合适的菜才是结果 | `PM15`、`DATA01` / [S25](https://www.svpg.com/product-management-an-introduction/)、[S26](https://www.svpg.com/the-product-operating-model-an-introduction/) |
| **JTBD** | 从触发情境、目标进展和现有替代描述用户待完成的任务 | 顾客买的可能不是牛肉面，而是十分钟内吃饱且不耽误开会 | `PM02` / [S27](https://www.producttalk.org/glossary-discovery-product-discovery/)、[S31](https://www.strategyzer.com/library/the-value-proposition-canvas) |
| **OST 机会解决方案树** | 目标→用户机会→候选方案→待验证假设的可视化决策结构 | 先找病因再选药，不是先指定某种药再去硬找病人 | `PM13` / [S28](https://www.producttalk.org/getting-started-with-discovery/) |
| **MVP 最小可行产品** | 以最低投入验证关键假设的可用方案，不等同功能粗糙或无限简化的生产系统 | 先在小摊验证有人肯点，再决定是否装修大店 | `PM06`、`PM07` / [S34](https://www.atlassian.com/agile/product-management/new-product-development-process)、[S27](https://www.producttalk.org/glossary-discovery-product-discovery/) |
| **Product-Market Fit** | 目标用户在市场中持续采用并从产品获得足够价值的证据性状态，不能由自评或单次点赞认定 | 不是朋友说好吃，而是顾客持续回来买并愿意承担价格 | `PM05`、`BIZ06`、`DATA02` / [S31](https://www.strategyzer.com/library/the-value-proposition-canvas)、[S25](https://www.svpg.com/product-management-an-introduction/) |
| **PRD** | 明确用户任务、范围、行为、异常状态和可测试验收的协作契约 | 厨房拿到菜谱就知道放什么、何时算熟，而不是猜老板想法 | `PM07` / [S02](https://www.atlassian.com/agile/product-management/requirements) |
| **RICE** | Reach×Impact×Confidence÷Effort 的相对排序工具，输入含主观估计需注明 | 先看多少人需要、帮助多大、把握多高、做起来多费劲 | `PM06` / [S35](https://www.atlassian.com/agile/product-management/prioritization-framework) |
| **OKR 与 North Star** | OKR 定义目标和关键结果，北极星定义反映用户核心价值的长期观测指标 | 希望顾客吃得好是目标；复购有效订单是可能的衡量方式，不是新发多少传单 | `PM15`、`DATA01` / [S36](https://www.atlassian.com/agile/product-management/product-operating-model) |
| **Product Operating Model** | 组织中的目标、授权、发现、交付、度量和治理如何共同运作 | 不是多雇厨师，而是全员知道点单、采购、出餐、反馈该怎样接力 | `PM18` / [S26](https://www.svpg.com/the-product-operating-model-an-introduction/)、[S36](https://www.atlassian.com/agile/product-management/product-operating-model) |
| **Roadmap** | 将产品战略表达为可调整的主题与结果优先级，不等同承诺所有功能的日历表 | 菜单开发方向可改，不能靠画日历证明菜会有人买 | `PM06` / [S03](https://www.atlassian.com/agile/product-management/product-roadmaps) |
| **UX Research** | 根据探索/评估目标选择访谈、观察、可用性测试、日志与量化实验 | 问客人为什么没吃、看他哪里卡住、统计多少客人离开，方法各不同 | `PM14` / [S29](https://www.nngroup.com/articles/which-ux-research-methods/) |
| **Service Blueprint** | 将用户接触点与后台人员、系统及失败交接绘成一张服务流程图 | 前台点单、后厨备料、外卖配送要对上，否则页面好看也没用 | `PM20` / [S29](https://www.nngroup.com/articles/which-ux-research-methods/) |
| **RACI/Stakeholder** | 清楚谁执行、最终负责、需咨询、应知会，以减少跨团队冲突 | 厨师做菜、店长拍板、财务审核、服务员收到通知 | `PM16` / [S36](https://www.atlassian.com/agile/product-management/product-operating-model) |
| **Business Model Canvas** | 九个要素解释产品如何创造、交付和获取价值 | 开店要同时算顾客、渠道、伙伴、资源、成本和收入 | `BIZ08` / [S30](https://www.strategyzer.com/library/the-business-model-canvas) |
| **Value Proposition Canvas** | 客户任务/痛点/收益与产品缓解痛点/创造收益之间的匹配假设 | 卖的是解决排队难、吃得快，而不是‘我们用了高级厨具’ | `BIZ08`、`PM05` / [S31](https://www.strategyzer.com/library/the-value-proposition-canvas) |
| **ICP/Buyer** | ICP 是高概率成功购买的组织画像，Buyer 是真正有付款/采购权的人 | 吃饭的人喜欢，不一定是决定团餐采购的负责人 | `BIZ06`、`BIZ07` / [S31](https://www.strategyzer.com/library/the-value-proposition-canvas) |
| **GTM** | 综合市场定位、定价、渠道、营销、销售和支持的上市协同方案 | 菜做好还得让对的人知道怎么买、怎么试、出了问题找谁 | `BIZ10` / [S34](https://www.atlassian.com/agile/product-management/new-product-development-process) |
| **CAC/LTV/贡献毛利** | 获客成本/客户生命周期价值与收入减直接可变成本各有口径，不等于净利润或现金流 | 顾客每单挣钱，不代表付完房租、营销和库存仍有钱 | `BIZ02`、`BIZ09` / [S30](https://www.strategyzer.com/library/the-business-model-canvas) |
| **现金流 Cash Flow** | 实际资金流入流出及时间，独立于利润和订单额 | 今天要付房租，平台下月结算，账面盈利也可能没钱 | `BIZ09` / [S30](https://www.strategyzer.com/library/the-business-model-canvas) |
| **Experiment/A-B** | 事先约定随机分组、目标/守门指标与分析规则，以减少虚假因果结论 | 隔两家相近分店测菜单，不能只挑最火那天的店 | `DATA03`、`COG02` / [S29](https://www.nngroup.com/articles/which-ux-research-methods/) |
| **LLM Eval** | 在版本固定的数据集与人工协议下检验质量、时延、成本、安全，不以模型自夸代替评测 | 主厨自称好吃不算，要盲测、记录错单和成本 | `AI11` / [S05](https://developers.openai.com/api/docs/guides/evaluation-best-practices) |
| **Workflow vs Agent** | 固定工作流按预设步骤执行；Agent 在边界内依据状态动态选择行动 | 固定套餐照菜单做；遇见复杂客诉才让授权店长判断下一步 | `AI05` / [S06](https://www.anthropic.com/engineering/building-effective-agents) |
| **Human-in-the-Loop** | 对高风险决策/外部动作保留人的审核、接管、撤销能力 | 退款和改订单不能只听机器人一句话就自动扣钱 | `AI05`、`AI12` / [S40](https://pair.withgoogle.com/guidebook-v2/chapters) |
| **Product Risk 四风险** | 价值、可用性、可行性、商业可持续性需要并行评估且权重随任务而变 | 会做一道菜，不代表有人点、吃得顺利、材料够且卖一份不亏 | `PM22` / [S25](https://www.svpg.com/product-management-an-introduction/)、[S26](https://www.svpg.com/the-product-operating-model-an-introduction/) |

## 三种典型误解，必须纠正

1. **“我写完 PRD 就是 PM”** → PRD 是沟通和验收的媒介，若问题/用户/反证是假的，写得越精美风险越大。回到 PM02、PM03、PM13。
2. **“用 AI 生成页面就等于产品上线”** → 没有合法数据授权、租户权限、故障恢复、支持和用户 UAT 的系统只是练习环境。回到 ENG06、OPS01–OPS06。
3. **“有人评论或点赞证明市场存在”** → 公开热度只能形成待验证假设；买家行为、试点、正式成交等证据必须分别判定。回到 BIZ06、BIZ08、COG01。

## 由点带面的三个例子

**A. ‘客户说要做 AI 知识库’** → 从 PM02（任务是什么）入手，向外延伸 PM03 用户行为 → PM04 非 AI 替代 → AI03 RAG 评测 → PM09 可信 UX → BIZ01 谁付钱 → OPS06 上线。只有具体失败才进入深度检索/训练。

**B. ‘智能体工单上线后重复写订单’** → 从 ENG07 幂等/异步入手，回溯 AI05 工具边界 → ENG06 AuthZ → AI12 Prompt Injection → OPS02 Trace → PM22 风险计划；不先学完整 PM 历史。

**C. ‘功能越做越多但没有收入’** → 从 BIZ06 ICP/买方定位，连接 BIZ08 价值画布 → DATA01 真实任务结果 → BIZ11 价格验证 → BIZ09 现金流 → MGT01 资源取舍。

## 什么时候只需要理解，什么时候要会亲手做？

- **PM 负责可独立判断**：真实或合成用户证据、选型、指标口径、PRD、成本和合规风险；必要时使用 AI 辅助但保留人的判断。
- **PE 负责可运行**：把选定的业务场景实现为可测试、可恢复、安全的系统；仍必须说明为何做和替代方案。
- **Founder 可能兼任两者**：不能把岗位技能测试当市场证据，更不能把 AI 帮做当本人独立掌握。
